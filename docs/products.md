# Admin product API

## Implemented scope

Admins can list, inspect, create, update and soft-delete products. Every endpoint under `/api/admin/products` requires an authenticated account with the current `Admin` role. Missing or invalid authentication returns 401; a Customer account receives 403. The public catalog and product frontend remain pending.

The existing `Products` table and PostgreSQL `xmin` concurrency mapping support this feature. No additional migration, environment variable or RabbitMQ worker is required. Keep the database initialization and JWT configuration from [Local development](local-development.md) and [Authentication](authentication.md).

## Endpoints and DTOs

| Method and path | Input | Success |
| --- | --- | --- |
| GET /api/admin/products | `ProductListRequestDto`: page, pageSize, search, isActive, includeDeleted | 200 `ProductPageResponseDto` |
| GET /api/admin/products/{id} | Product UUID | 200 `ProductResponseDto`, including a soft-deleted product |
| POST /api/admin/products | `CreateProductRequestDto` | 201 `ProductResponseDto` with Location pointing to the detail endpoint |
| PUT /api/admin/products/{id} | Product UUID and `UpdateProductRequestDto` | 200 `ProductResponseDto` |
| DELETE /api/admin/products/{id}?version={version} | Product UUID and `DeleteProductRequestDto` query | 204, no body |

DTOs live in `Application/Products/Dtos`. Create and update DTOs contain only editable fields: `sku`, `name`, `description`, `price`, `stockQuantity`, `isActive`; update also requires `version`. IDs and timestamps are generated by the server. Sending entity-only fields does not control them. PUT supplies the full editable state, including an explicit null description to clear it.

| Field | Validation and behavior |
| --- | --- |
| sku | Required; raw input is at most 64 characters; the trimmed value starts with an ASCII letter/digit and contains only ASCII letters/digits, underscores or hyphens; normalized to uppercase; unique even across soft-deleted products |
| name | Required; trimmed length 2-200 |
| description | Optional/null; maximum 4,000 characters |
| price | Required; whole VND between 0 and 999999999999999999 inclusive; no fractional amount |
| stockQuantity | Required; integer between 0 and 2147483647 inclusive |
| isActive | Required true/false; false hides availability for future customer workflows without deleting the product |
| version | Required on update/delete; positive uint returned by the last product read; do not invent or increment it |

A product response contains `id`, `sku`, `name`, `description`, `price`, `stockQuantity`, `isActive`, `createdAt`, `updatedAt`, `deletedAt` and `version`. Timestamps use UTC; nullable timestamps are null until applicable. No EF or Identity entity is returned.

A page response contains `items`, `totalCount`, `page` and `pageSize`. Query defaults are `page=1`, `pageSize=20` and `includeDeleted=false`; page is 1-1,000,000, pageSize is 1-100, and search is at most 200 characters. Search is a literal, case-insensitive substring match on SKU or name; `%` and `_` do not act as search wildcards. Omit `isActive` to include both active and inactive products. Set `includeDeleted=true` to include soft-deleted rows as well. Results use `createdAt` descending and then `id` descending for stable ordering; an empty/out-of-range page returns an empty items array.

## Try the API locally

Start the API from the repository root:

```powershell
dotnet run --project backend/src/ESDEMO.Api
```

Log in at `POST /api/auth/login` using the seeded Admin's email and original password. Use the returned accessToken in your REST client or the local PowerShell session below. Do not commit actual tokens or passwords in request collections or scripts.

```powershell
$baseUrl = 'http://localhost:5000'
$headers = @{ Authorization = 'Bearer <accessToken-from-admin-login>' }

$createBody = @{
    sku = 'demo-keyboard-001'
    name = 'Demo Keyboard'
    description = 'Product for local API review'
    price = 350000
    stockQuantity = 10
    isActive = $true
} | ConvertTo-Json

$product = Invoke-RestMethod -Method Post -Uri "$baseUrl/api/admin/products" -Headers $headers -ContentType 'application/json' -Body $createBody

Invoke-RestMethod -Uri "$baseUrl/api/admin/products?page=1&pageSize=20&search=keyboard" -Headers $headers
```

The returned SKU is `DEMO-KEYBOARD-001`. Reusing that SKU returns 409, even after soft deletion. Use a new SKU when repeating the create example.

Read the current representation before editing and pass its version:

```powershell
$product = Invoke-RestMethod -Uri "$baseUrl/api/admin/products/$($product.id)" -Headers $headers

$updateBody = @{
    sku = $product.sku
    name = 'Demo Keyboard Updated'
    description = $null
    price = 375000
    stockQuantity = 8
    isActive = $true
    version = $product.version
} | ConvertTo-Json

$product = Invoke-RestMethod -Method Put -Uri "$baseUrl/api/admin/products/$($product.id)" -Headers $headers -ContentType 'application/json' -Body $updateBody

Invoke-RestMethod -Method Delete -Uri "$baseUrl/api/admin/products/$($product.id)?version=$($product.version)" -Headers $headers
Invoke-RestMethod -Uri "$baseUrl/api/admin/products?includeDeleted=true" -Headers $headers
```

The product remains stored with `isActive=false` and `deletedAt` set. The default list no longer includes it; Admin detail reads still return it. Its SKU and any existing order history references remain intact. Updating or deleting an already deleted product returns 404; there is no restore or permanent-delete endpoint.

## Concurrency and errors

`version` represents the row's PostgreSQL `xmin`. It changes after an update. Store the returned version alongside the product and send it on the next update/delete. If another request changes the row first, the API returns 409 instead of overwriting that change. Fetch the latest product, review the changes and then retry with the new version. Do not automatically replace the version and retry an old edit without reviewing the current data.

Errors use ProblemDetails with a traceId. Validation returns 400 with field errors; unknown IDs and mutations of deleted products return 404; duplicate SKUs and stale versions return 409. Authentication/authorization returns 401/403 as described above. Request bodies over 32 KiB return 413. Known validation/not-found/conflict responses do not expose provider details. Unexpected exception detail follows the global environment policy and is hidden outside Development.

Application handlers own the product mutation and use a feature-specific repository interface in Application. Infrastructure implements persistence with EF Core; read queries project directly to DTOs without tracking. HTTP validation and the MediatR validation behavior both enforce DTO rules. Each write uses a single atomic SaveChanges operation, with the database uniqueness and concurrency checks also covering competing requests. Product CRUD does not require an outgoing event or an explicit transaction spanning multiple saves.
